# Summary

## Core idea
You're adding a **knowledge mode** to your existing worker agent — not a new subsystem. 
The same execution machinery (context management, compaction, tool orchestration, 
history) is reused; only the toolset, system prompt, objective, and turn budget change. 
Think of it as `worker.run(task, available_tools=KNOWLEDGE_TOOLS, max_turns=12)`.

## The two tools to build (nothing else this iteration)
1. **`search_information(query, info_types, execution_ids, source_ids, item_ids, 
limit)`**
   - Generalised semantic search over your existing `InfoChunk` representation.
   - Expose *named* filters (not raw DB expressions) so the agent doesn't need to know 
your vector store schema.
   - Every result carries **provenance** (which execution, source episode, type, 
instance) so the worker can trace a claim back to where it came from.
   - Vector match ≠ evidence; it's a pointer *to* evidence.

2. **`propose_relationship(source_chunk_id, target_chunk_id, relationship_type, 
explanation)`**
   - Creates a **new derived object** (a `ProposedRelationship`) that links two existing 
chunks. It never mutates them and never asserts truth.
   - Keep the relationship vocabulary small: `RELATED_TO, SUPPORTS, CONTRADICTS, REFINES, 
GENERALIZES, SPECIALIZES`. Defer finer-grained assessments (tension vs. genuine 
contradiction, scope divergence) to a later process.
   - Enforce referential integrity (both IDs must exist); flag but don't silently drop 
duplicate proposals (two runs proposing the same link is itself data).

## Other small additions
- **Remaining-turn counter** in the worker's context (e.g. "4 turns left"). Reserve the 
final turn for synthesis/reporting. This is what stops an otherwise open-ended 
exploration from running forever.
- **Log the selected toolset** in the execution record so you can tell *which mode* 
produced a given episode.
- **Preserve the discovery process.** Your immutable execution history already captures 
the turn-by-turn reasoning (what was searched, what was retrieved, why a relationship was 
proposed). That process is more valuable than the two edges it produced, and it lets you 
A/B compare models/prompts on the same knowledge snapshot.

## What to deliberately *not* do yet
No principles, no propositions, no belief snapshots, no automated synthesis, no new 
services/agent classes/DB abstractions. The open question this iteration answers is: *can 
a bounded worker, given access to its accumulated InfoChunks, independently find 
relationships that are genuinely useful, non-obvious, and well-supported by provenance?* 
Either answer teaches you something concrete about retrieval, prompts, vocabulary, or 
model limits.

## Suggested scope for today (in order)
| # | Task | Why |
|---|------|-----|
| 1 | InfoChunk semantic-search tool | Enables discovery |
| 2 | `propose_relationship` tool | Enables graph enrichment |
| 3 | Toolset-selection argument on the worker | Separate operating modes |
| 4 | Remaining-turn visibility in context | Bounded exploration |
| 5 | Run one small discovery experiment | Test the whole loop end-to-end |

## The experiment to run
Give the knowledge worker a narrow prompt (e.g. *"Find up to 5 meaningful relationships 
among context-management chunks; prioritise recurring patterns, tensions, contradictions; 
cite existing chunks; don't conflate semantic similarity with reasoning."*), run it with 
a fixed turn budget, then manually inspect:
- How many proposed relationships are actually useful vs. just semantically similar?
- Does the worker actively seek contradictory evidence, or does it just reinforce its 
first interpretation?

That third question matters most.

## The bigger picture (one paragraph)
The Prigogine thread reinforces the framing: knowledge is a **process of becoming**, not 
a static store. Two knowledge graphs with identical content but different histories are 
*different* systems, and your immutable execution history is what preserves that 
distinction. The normal worker **generates** experience; the knowledge worker 
**reorganises the interpretation** of that experience. Neither is "the" source of truth. 
When you eventually let the normal worker read the knowledge framework, you get a 
feedback loop where accumulated understanding shapes future action and future action 
reshapes accumulated understanding — which is where this starts to get genuinely 
interesting.

> The practical takeaway: build exactly the two tools, make the worker configurable, add 
the turn budget, run one experiment, and look at the output. Don't let today's momentum 
turn into another three days of scaffolding before you've seen the first knowledge worker 
do something real.

# Summary

You've landed on a solid architectural direction: instead of building a *new* agent, add 
a **knowledge mode** to your existing worker-agent. The worker's infrastructure (context 
management, compaction, distillation, tool orchestration, episode extraction) all carries 
over. Only its **toolset and mission** change.

## Core Architectural Idea

```
WORKER AGENT
     |
  ┌──┴──┐
  ↓     ↓
EXECUTION MODE  KNOWLEDGE MODE
(existing tools)  (knowledge tools)
  └──┬──┘
     ↓
CONTEXT → DISTILLATION → EXECUTION HISTORY → EPISODE EXTRACTION
```

Toolset selection is an explicit invocation parameter (`toolset="knowledge"`), which 
makes it an **experimental variable** you can log and compare.

## Two New Tools

**1. `search_infochunks`** – a thin wrapper over your existing evidence search. Key 
properties:
- Returns full `InfoChunk` metadata (provenance, execution IDs, etc.), not just text + 
score.
- Supports filtering by `info_type`, `execution_id`, `source_id`.
- Vector similarity is treated as a **search heuristic**, not evidential weight.
- Notably, you can search for `AgentStateDelta.Understandings` to investigate *changes* 
in understanding, not just accumulated conclusions.

**2. `propose_relationship`** – creates a **persisted, distinct object** (a 
`ProposedRelationship`) rather than immediately writing an edge into the graph.
- Each proposal references specific `InfoChunk` IDs as supporting evidence.
- Separates **observations** (InfoChunks) from **interpretations** (relationships).
- Allows cross-type relationships (Grist→Principle, Episode→Proposition, etc.) without a 
rigid matrix.
- Includes a short natural-language **rationale** field.
- Endpoints are mechanically validated.

Relationships stay in a `PROPOSED` state; they don't auto-promote to established edges.

## Key Design Decisions & Cautions

- **Prigogine / dissipative-structures framing:** The graph is a *projection* of an 
ongoing history of transformations, not the process itself. The arrow of time is baked 
into the system — you can't reconstruct "how we got here" from the final graph alone. 
Preserve that distinction in implementation.
- **Stay narrow.** The initial knowledge worker does *one* thing: identify and propose 
relationships between existing InfoChunks. No principle-creation, 
contradiction-resolution, or belief-modification yet.
- **Bound exploration.** Expose remaining-turn count to the agent, but the *harness* 
enforces the hard limit. The system prompt should say uncertainty is an acceptable 
outcome and that 5 good relationships > 30 speculative ones. The agent should also be 
allowed to **finish early** if it judges useful work exhausted.
- **Record toolset version** in execution metadata for reproducibility.

## Suggested Build Sequence (in order)

| # | Work |
|---|------|
| 1 | `search_infochunks` tool |
| 2 | `propose_relationship` tool |
| 3 | Toolset selection mechanism |
| 4 | Remaining-turn awareness in the prompt |
| 5 | Run a few knowledge-exploration executions and **inspect** |

Resist adding more infrastructure until you've seen what actually happens.

## Suggested First Experiment

Feed the knowledge worker InfoChunks from a set of historical executions about context 
management. Give it **no** existing principle to discover. Ask it to find meaningful 
relationships. Then look for:
- Relationships not obvious from any single observation?
- Can it tell apart *genuinely supporting* vs *merely similar* observations?
- Does it surface **tensions and contradictions**, or does it just reinforce existing 
assumptions?

If it only consolidates, you've built a confirmation engine. If it challenges, you've 
started building something genuinely interesting.

## Closing Thought

The author draws a parallel to your friend's Psalm ("a shield around me"): a shield's 
meaning is *relational* — it only exists in reference to the threat. Likewise, concepts 
and principles don't have meaning in isolation; their significance emerges through 
relationships, contexts, and history. And relationships can shift while the original 
experiences remain immutable.

> **The history is immutable. The interpretations are revisable. The beliefs are 
snapshots.**

Build the two tools, add toolset selection, expose the turn budget, and stop there. Let 
the experiment teach you what comes next.

# 5 Biggest Differences Between the Two Options

## 1. Architecture Topology: Convergence vs. Linear Pipeline

The two options draw the system differently, and this is a genuine structural commitment, 
not just a diagrammatic choice.

**Option 1** shows the two modes (Execution / Knowledge) as *parallel branches* that both 
converge into a shared **Context Management → Episode Extraction** layer. The implication 
is that both modes operate over the same substrate and share the same downstream 
processing.

**Option 2** shows a *linear waterfall*: Worker → (two modes) → Context Management → 
**Distillation → Execution History → Episode Extraction**. Here, context management feeds 
into a sequential chain where distillation, execution history, and episode extraction are 
distinct stages flowing one after the other.

This matters because Option 1 frames context management and episode extraction as *shared 
services* both modes invoke. Option 2 frames them as a *pipeline* the worker's output 
passes through. The first is more like a hub-and-spoke; the second is more like a flow.

---

## 2. Tool 2 Schema: Fixed Vocabulary vs. Flexible Properties

This is perhaps the most consequential design fork.

**Option 1** prescribes a flat, closed vocabulary:

```python
RELATED_TO, SUPPORTS, CONTRADICTS, REFINES, GENERALIZES, SPECIALIZES
```

The `ProposedRelationship` model is flat: `source_chunk_id`, `target_chunk_id`, 
`relationship_type`, `explanation`, `originating_execution_id`, `status`, `created_at`. 
Relationships are between InfoChunks and InfoChunks, nothing else.

**Option 2** uses an open `properties: dict` and a `supporting_infochunks: list[str]` 
field. The example relationship type is `"POTENTIALLY_SUPPORTS"` (note the hedging). It 
explicitly anticipates cross-type relationships:

```
Grist → Principle
Grist → Proposition
Principle → Concept
Principle → Principle
Episode → Principle
```

Option 1's approach is more *bounded* (good for a first experiment, easier to review). 
Option 2's approach is more *permissive* (more flexible, but the agent has more freedom 
to propose things the harness may not want to store).

---

## 3. A Dedicated "Preserve the Discovery Process" Design Principle

**Option 1** devotes an entire section (section 5) to the idea that the *process of 
arriving at the relationships* is more valuable than the relationships themselves. It 
lays out a worked 7-turn example and explicitly argues that the immutable execution trace 
gives you the ability to *compare different models or prompts* running the same discovery 
task.

**Option 2** touches on this idea implicitly (the execution history is part of the 
pipeline, provenance is preserved in each tool's output), but it never elevates it to a 
*first-class design principle* or argues for the comparative-experiment use case.

This isn't a trivial difference. Option 1 is saying "your architecture already does the 
hard part — the trace — so design the tools to *serve* that trace, and treat the trace as 
the primary artifact." Option 2 says the trace is part of the system but doesn't make it 
the *organising principle* of this iteration.

---

## 4. Turn Budget: Reserve the Final Turn vs. Allow Early Completion

Both options agree on the need for a bounded budget and on exposing remaining turns to 
the agent. They diverge on *how the budget ends*.

**Option 1** (12 turns) explicitly says: *"I'd reserve the final turn for synthesis and 
reporting, rather than allowing the worker to consume its entire budget on retrieval."* 
The budget is a fixed allocation, and the last unit is *mandated* for a wrap-up. You get 
a reminder at 2 remaining. The shape of the run is predetermined.

**Option 2** (8 turns) explicitly says: *"allow the worker to finish early. It should be 
able to conclude that it has exhausted the useful work available."* And: *"Five genuinely 
useful relationships are preferable to thirty speculative ones."* The budget is a 
ceiling, not a floor, and the agent can stop before it's spent.

Option 1 optimises for *consistency of output* (every run ends with a synthesis turn). 
Option 2 optimises for *quality over quantity* (the agent earns the right to stop). They 
produce different failure modes: Option 1 risks forced, low-quality synthesis turns when 
the work is done; Option 2 risks the agent stopping too early because it misjudges 
"useful work available."

---

## 5. The Prigogine Framing: "Process of Becoming" vs. "Graph as Projection"

Both options engage the Prigogine connection, but they land on subtly different 
*metaphysical* commitments that shape downstream design.

**Option 1** frames knowledge as *"a process of becoming, not merely a collection of 
stored conclusions."* The central claim is that *two knowledge systems with identical 
content can have different histories, and the history matters.* It specifically says "the 
interesting thing isn't simply the resulting knowledge graph. It's the process through 
which that graph developed." The graph is a *snapshot of a process*, and the process is 
the primary object of interest. This leads to its explicit recommendation to version 
synthesis (you're versioning the *process*, not just the output).

**Option 2** frames the knowledge graph as *"a projection of an ongoing historical 
process, not as the process itself."* The central claim is structural: the graph is a 
*projection*, and the projection is lossy. It maps specific system components onto 
Prigogine's vocabulary (execution = energy flow, distillation = transformation, synthesis 
= pattern identification). The emphasis is on the *pipeline* and on the fact that you 
can't reconstruct the history from the current graph state.

The practical difference: Option 1's framing pushes you to *preserve and version the 
process itself* (version synthesis, keep the trace as primary). Option 2's framing pushes 
you to *treat the graph as a derived, revisable projection* (the history is immutable, 
the interpretations are revisable, the beliefs are snapshots — the graph is one of those 
interpretations). They're compatible, but they pull in slightly different directions on 
what you *optimise for* in the architecture.




Option 1, and it's not a close call. Here's why:

**The "preserve the discovery process" section is the load-bearing insight.** Option 1 
says, essentially: *the trace is the primary artifact, not the graph edges.* It gives you 
the comparative-experiment framing ("run the same discovery task with different 
models/prompts"). Option 2 has the pieces in the pipeline but never *commits* to that as 
a design principle. The risk with Option 2 is that you build the two tools, run the 
experiment, and then three weeks later realise you didn't actually care about the trace 
because nothing in the design made you protect it. Option 1 makes it non-negotiable up 
front.

**For a first experiment, the closed vocabulary is the better call.** Option 1's six 
relationship types are a *constraint* you can review, count, and reason about. Option 2's 
`properties: dict` is more elegant as a schema, but in the first experiment it means the 
agent can propose anything, and you'll have to manually sift through an open-ended 
namespace to figure out what it's actually doing. You can always open it up in v2. The 
whole point of this iteration is "can a constrained worker find useful relationships?" — 
give it the constraint.

**Reserving the final turn beats "allow early completion."** I've watched enough agent 
runs to know that "you may stop when you're done" tends to produce either premature 
stopping (the agent feels satisfied after two searches) or the agent never declaring 
itself done because it can always find one more adjacent thing. A fixed 
final-turn-for-synthesis structure is more predictable and, in practice, produces better 
summaries than whatever the agent would produce on its own volition at turn 11 of 12. You 
still get the "five good > thirty speculative" principle by just putting it in the 
final-turn instructions.

**The feedback-loop closing is more actionable.** *"The normal worker generates 
experience. The knowledge worker reorganises the interpretation of experience. Eventually 
they form a feedback loop."* That's a sentence you can put on a wall and it guides every 
future design decision. Option 2's Psalm framing is lovely — "a shield around me" as a 
relational ontology is genuinely a nice metaphor — but it's a *reflection*, not a 
*directive*.

That said, I'd steal a few specific things from Option 2:

- The concrete `InfoChunk` schema. Option 1 describes it in prose; Option 2 gives you the 
fields. Use Option 2's.
- The `AgentStateDelta.Understandings` example. That's a specific, useful search target 
that Option 1 doesn't mention, and it's the kind of query you'll actually want in your 
first experiment.
- The "five genuinely useful relationships are preferable to thirty speculative ones" 
phrasing — good enough to put in the system prompt verbatim.
- The `supporting_infochunks: list[str]` field in `ProposedRelationship`. Option 1's 
single `explanation` string is a bit thin. Even with the closed vocabulary, I'd want the 
agent to be able to point at specific chunks that *support* the proposed relationship, 
not just describe it in prose.

So: build Option 1's system, with Option 2's schema details and that one extra field on 
the proposed relationship. That's where I'd be on Friday afternoon.
